= Probar inferencia

El modelo en MaaS se llama con API key.

== Prerrequisito: Authorino

El script `apply-maas.sh` aplica los fixes de Authorino al final (service CA + gRPC TLS). Dos fallos conocidos, corregidos por ese paso:

* `/v1/models` o el chat responden `AUTH_FAILURE` / `Exception thrown while generating token` con una API key válida → Authorino no confía en el TLS de `maas-api` (service CA).
* `POST /maas-api/v1/api-keys` devuelve *HTTP 500* y el dashboard falla con `unmarshall: invalid character 'I'` → el EnvoyFilter `openshift-ai-inference-authn-ssl` habla TLS a Authorino `:50051` y el listener de Authorino está en plaintext. No intentes quitar el TLS con DestinationRule.

Si reaparecen (p. ej. el gateway se regenera), re-ejecuta `bash manifests/apply-maas.sh` (idempotente; vuelve a aplicar los fixes y el smoke test).

== API key

Usa el **mismo** nombre de subscription del módulo 9 (`qwen-authenticated`). Si creaste otra en la UI (p. ej. `demo`), cámbiala en el JSON.

[source,bash]
----
CLUSTER_DOMAIN=$(oc get ingresses.config/cluster -o jsonpath='{.spec.domain}')
MAAS_URL="maas.${CLUSTER_DOMAIN}"
echo "https://${MAAS_URL}"

oc get maassubscription -n models-as-a-service

API_KEY=$(curl -sk -X POST "https://${MAAS_URL}/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -H "Content-Type: application/json" \
  -d '{"name":"workshop","subscription":"qwen-authenticated","expiresIn":"8h"}' \
  | jq -r '.key')

echo "$API_KEY"
----

Si imprime `null`, la subscription no existe, el nombre no coincide, o el POST devolvió HTTP 500 (script de gRPC TLS arriba). Revisa el error completo sin `jq -r '.key'`.

== Listar modelos y chatear

IMPORTANT: El Qwen CPU del lab tiene `max_model_len=2048`. Pide **`max_tokens` ≤ 1024** (64 en smoke). Con 4096 verás `invalid_prompt` / `max_tokens cannot be greater than max_model_len`.

[source,bash]
----
curl -sk "https://${MAAS_URL}/v1/models" \
  -H "Authorization: Bearer ${API_KEY}" | jq

MODEL_ID=$(curl -sk "https://${MAAS_URL}/v1/models" \
  -H "Authorization: Bearer ${API_KEY}" \
  | jq -r '.data[0].id')

curl -sk "https://${MAAS_URL}/v1/chat/completions" \
  -H "Authorization: Bearer ${API_KEY}" \
  -H "Content-Type: application/json" \
  -d "{
    \"model\": \"${MODEL_ID}\",
    \"messages\": [{\"role\":\"user\",\"content\":\"Say hello in one sentence. /no_think\"}],
    \"max_tokens\": 64
  }" | jq
----

El `id` suele ser `publishers/llm/models/qwen3-06b`.

== UI — Models as a Service

Dashboard → *Models as a Service* → el modelo → *Playground*. Usa `/no_think` y `max_tokens` bajo (≤ 1024).

== UI — Gen AI Studio Playground

Gen AI Studio crea el `OGXServer` `lsd-genai-playground` *la primera vez* que abres Playground en el proyecto `llm`. Hasta entonces `oc get ogxserver -A` está vacío y el script de abajo falla `NotFound`.

. Abre *Gen AI Studio* → *Playground* → proyecto `llm` (con eso basta para crear el CR).
. El `OGXServer` usa por defecto `VLLM_API_TOKEN=fake` y `VLLM_MAX_TOKENS=4096` → *403* y *invalid_prompt* (4096 > 2048). Con `curl` ya funcionando:

[source,bash]
----
bash manifests/fix-playground-maas.sh
----

. *New chat* → elige el modelo MaaS (`…/publishers/llm/models/qwen3-06b`) → mensaje con `/no_think`.

NOTE: Si el dashboard regenera el `OGXServer`, puede volver `fake` / `4096`. Vuelve a ejecutar el script.
